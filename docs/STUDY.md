# 시스템 리소스 관리, 교착상태 및 장애 커뮤니케이션 정리

---

## 1. OOM Killer와 MemoryGuard의 차이

OOM(Out Of Memory)은 메모리 할당 요청을 처리할 수 있는 여유 메모리가 부족해진 상태를 말한다. 다만 메모리 부족을 감지하고 대응하는 주체는 환경에 따라 다르다.

### OOM Killer (Out-Of-Memory Killer)

- **주체:** 리눅스 커널
- **동작 시점:** 시스템 전체 또는 특정 메모리 제어 그룹(cgroup)에서 메모리 할당이 어려워 OOM 상황이 발생했을 때 동작할 수 있다.
- **역할:** 메모리를 확보하기 위해 종료할 프로세스를 선택하고 `SIGKILL`을 보내 강제 종료한다.
- **선정 방식:** 메모리 사용량 등을 바탕으로 계산되는 `oom_score`가 주요 판단 요소다. `/proc/PID/oom_score_adj`로 프로세스별 점수에 영향을 줄 수 있다.

OOM Killer가 동작하려면 시스템 RAM과 Swap이 모두 완전히 소진되어야 하는 것은 아니다. Docker나 Kubernetes처럼 cgroup 메모리 한도를 사용하는 환경에서는 해당 한도에 도달해 컨테이너 내부에서 OOM이 발생할 수도 있다.

### MemoryGuard (애플리케이션 메모리 보호 정책)

MemoryGuard는 리눅스 커널의 표준 기능명이 아니라, 특정 애플리케이션이나 솔루션이 메모리 사용량을 감시하고 정해진 정책에 따라 대응하는 기능을 가리키는 이름으로 사용될 수 있다.

- **주체:** 애플리케이션 또는 별도 소프트웨어
- **동작 시점:** 설정한 메모리 임계치에 도달하거나 메모리 사용량이 위험 수준이라고 판단했을 때
- **대응 방식:** 신규 작업 제한, 캐시 정리, 경고 출력, 자체 종료 또는 외부 프로세스 종료 요청 등 구현에 따라 다르다.

따라서 미션의 `agent-leak-app`에서 `MemoryGuard` 로그와 `SELF-TERMINATED` 메시지가 확인된다면, 우선 애플리케이션 내부 보호 정책이 종료를 결정했는지 살펴봐야 한다. 이 로그만으로 커널 OOM Killer가 작동했다고 결론 내리면 안 된다.

### 핵심 비교

| 구분 | OOM Killer | MemoryGuard |
|---|---|---|
| 주체 | 리눅스 커널 | 애플리케이션 또는 별도 솔루션 |
| 목적 | 메모리 할당 실패 상황에서 메모리 확보 | 설정된 정책에 따라 메모리 사용량 제어 |
| 대응 | 프로세스에 `SIGKILL` 전송 | 경고, 작업 제한, 캐시 정리, 종료 등 구현에 따라 다름 |
| 확인 근거 | 커널 로그, cgroup 메모리 이벤트 등 | 애플리케이션 로그와 설정값 |

## 2. 종료 코드 137과 143

리눅스 셸과 컨테이너 환경에서는 프로세스가 시그널에 의해 종료된 경우 관례적으로 `128 + 시그널 번호` 형태의 종료 상태가 관측된다.

### 종료 코드 137 (`128 + 9`, SIGKILL)

- **의미:** 프로세스가 `SIGKILL`을 받아 강제 종료된 경우 흔히 관측되는 종료 코드다.
- **특징:** 프로세스가 시그널을 처리하거나 무시할 수 없으며, 정리 작업을 수행할 기회를 보장받지 못한다.
- **가능한 원인:** 커널 OOM Killer, `kill -9 PID`, 종료 유예 시간 초과 후 강제 종료 등.

### 종료 코드 143 (`128 + 15`, SIGTERM)

- **의미:** 프로세스가 `SIGTERM`을 받아 종료된 경우 흔히 관측되는 종료 코드다.
- **특징:** 종료 요청을 애플리케이션이 처리할 수 있다. 진행 중인 작업 정리, 연결 종료, 파일 저장 등을 수행하도록 구현할 수 있다.
- **가능한 원인:** `kill PID`, `docker stop`, Kubernetes의 Pod 종료 등.

`SIGTERM`을 받았다는 사실만으로 정상적인 정리 절차가 완료됐다고 단정할 수는 없다. 애플리케이션이 시그널을 어떻게 처리했는지와 종료 로그를 함께 확인해야 한다. 마찬가지로 종료 코드 137만으로 OOM이 원인이라고 확정할 수 없다.

### Graceful Shutdown

Graceful Shutdown은 프로세스를 즉시 끊는 대신, 새로운 작업 수신을 중단하고 진행 중인 작업과 연결을 정리한 뒤 종료하는 절차다. 일반적으로 `SIGTERM`을 계기로 시작하며, 제한 시간 안에 종료하지 못하면 운영 환경이 `SIGKILL`을 보낼 수 있다.

| 구분 | 종료 코드 137 | 종료 코드 143 |
|---|---|---|
| 흔히 연관되는 시그널 | `SIGKILL` (9) | `SIGTERM` (15) |
| 종료 방식 | 강제 종료 | 종료 요청 |
| 애플리케이션의 정리 작업 | 수행 기회가 보장되지 않음 | 시그널 처리기를 구현했다면 수행 가능 |
| 원인 판단 | OOM, 수동 강제 종료, 타임아웃 등 추가 확인 필요 | 배포·중지 요청 등 추가 확인 필요 |

## 3. Memory Leak과 OOM

### 개념과 차이

- **Memory Leak(메모리 누수):** 프로그램이 더 이상 필요하지 않은 메모리를 계속 참조하거나 반환하지 않아, 사용 가능한 메모리가 점차 줄어드는 현상이다.
- **OOM(Out Of Memory):** 메모리 할당에 필요한 여유 공간을 확보하지 못하는 상태 또는 그로 인한 장애다.

메모리 누수는 OOM의 원인 중 하나지만, 모든 OOM이 메모리 누수 때문에 발생하는 것은 아니다. 순간적인 대용량 할당, 트래픽 급증, 비정상적으로 큰 캐시, 메모리 한도 설정 등도 OOM을 유발할 수 있다.

| 구분 | Memory Leak | OOM |
|---|---|---|
| 본질 | 메모리가 회수되지 않는 현상 또는 결함 | 메모리 할당이 어려워진 상태 |
| 발생 양상 | 장시간에 걸쳐 점진적으로 나타날 수 있음 | 점진적 또는 순간적으로 발생 가능 |
| 관계 | OOM을 일으키는 원인 중 하나 | 누수 외에도 다양한 원인으로 발생 |
| 대응 | 누수 원인 분석 및 코드 수정 | 원인에 따라 최적화, 한도 조정, 증설 등 |

### 프로세스 메모리 영역

- **Code(Text) 영역:** 실행할 기계어 코드가 저장되는 영역이다.
- **Data 영역:** 전역 변수와 정적 변수가 저장되는 영역이다.
- **Stack 영역:** 함수 호출 정보, 지역 변수 등이 저장되는 영역이다. 함수 호출이 끝나면 해당 호출 프레임이 정리되므로 일반적으로 동적 메모리 누수의 주된 원인은 아니다.
- **Heap 영역:** 동적 메모리 할당이 이루어지는 영역이다. 직접 메모리를 관리하는 환경에서는 해제 누락이 발생할 수 있고, GC를 사용하는 환경에서도 객체 참조가 불필요하게 유지되면 메모리가 회수되지 않을 수 있다.

메모리 누수는 Heap에서 흔히 관찰되지만, 메모리 매핑, 네이티브 메모리, 파일 디스크립터 등 다른 자원의 누수와 구분해서 살펴볼 필요가 있다.

### 메모리 사용량을 읽는 주요 지표

| 지표 | 의미 | 해석 시 주의점 |
|---|---|---|
| RSS (`VmRSS`) | 현재 물리 메모리에 적재된 프로세스 메모리 | 공유 페이지가 포함될 수 있다 |
| VSZ (`VmSize`) | 프로세스가 확보한 가상 주소 공간의 크기 | 실제 RAM 사용량과 같지 않다 |
| PSS | 공유 메모리를 공유 프로세스 수에 따라 나눠 반영한 값 | 프로세스의 메모리 부담을 비교할 때 참고할 수 있다 |
| VmHWM | 프로세스가 기록한 최대 RSS | 현재 사용량이 아니라 최대 기록이다 |
| Private Dirty | 해당 프로세스에 사적으로 귀속된 수정 메모리 | 실제 메모리 증가 원인을 분석할 때 참고한다 |

RSS가 지속적으로 증가하면 실제 물리 메모리 점유가 증가하고 있을 가능성이 있다. 반면 VSZ만 증가했다고 실제 RAM을 그만큼 사용한다고 볼 수는 없다. 어떤 단일 지표만으로 메모리 누수를 확정하지 말고, 시간에 따른 추이와 애플리케이션 동작을 함께 살펴야 한다.

### 메모리 누수가 시스템에 미칠 수 있는 영향

1. **메모리 여유 감소:** 프로세스가 메모리를 계속 점유하면 시스템의 `MemAvailable`이 감소하고 다른 프로세스가 사용할 수 있는 메모리가 줄어든다.
2. **GC 및 메모리 관리 비용 증가:** GC 기반 런타임에서는 객체와 힙 상태에 따라 GC 실행 빈도나 비용이 증가할 수 있다. 다만 모든 GC가 동일하게 Stop-The-World 방식으로 동작하는 것은 아니다.
3. **스와핑 및 성능 저하:** 메모리 압박이 심해지면 페이지 회수와 Swap I/O가 늘어날 수 있다. 이로 인해 해당 프로세스뿐 아니라 같은 시스템의 다른 프로세스도 느려질 수 있다.
4. **OOM 및 연쇄 장애 가능성:** 메모리 할당 실패나 OOM Killer 동작으로 프로세스가 종료될 수 있다. 재시작 후 누수가 반복되거나 남은 서버에 트래픽이 집중되면 장애가 확산될 수 있다.

## 4. CPU 사용률, CPU Latency 및 과점유

### CPU 사용률과 CPU Scheduling Latency

- **CPU 사용률(CPU Utilization):** 일정 시간 동안 CPU가 작업을 수행한 비율이다.
- **CPU Scheduling Latency:** 작업이 실행 가능한 상태가 된 후 실제 CPU를 할당받기까지 기다리는 시간이다.

CPU 사용률은 자원이 얼마나 바쁜지를 보여주고, 스케줄링 지연은 작업이 CPU를 얼마나 오래 기다렸는지를 보여준다. 둘은 관련이 있지만 같은 지표는 아니다.

CPU 사용률이 높으면 실행 대기열이 길어져 지연이 커질 수 있다. 반대로 전체 CPU 사용률이 낮더라도 특정 코어에 부하가 집중되거나 컨테이너 CPU 제한(Throttling)이 발생하면 특정 작업의 지연이 커질 수 있다.

### CPU 사용률과 Load Average

Load Average는 일정 시간 동안 실행 중이거나 실행을 기다리는 작업과, 중단 불가능한 I/O 대기 상태에 있는 작업의 평균적인 수를 나타낸다.

예를 들어 4개 CPU 코어를 가진 시스템에서 Load Average가 4보다 높다면 코어 수보다 많은 작업이 실행 또는 대기 중일 가능성이 있다. 다만 Load Average에는 CPU 실행 대기뿐 아니라 일부 I/O 대기 작업도 포함되므로 CPU 사용률과 동일하게 해석하면 안 된다.

### 멀티코어 환경의 프로세스 CPU 사용률

측정 도구의 표기 기준에 따라 프로세스 CPU 사용률은 100%를 초과할 수 있다. 한 코어를 완전히 사용한 상태를 100%로 표시하는 기준에서는 두 코어를 완전히 사용하면 200%로 나타날 수 있다.

따라서 `top`, `ps`, 애플리케이션 내부 지표를 비교할 때는 각 지표가 시스템 전체 기준인지, 프로세스 기준인지, 코어 하나를 100%로 보는지 확인해야 한다.

### 특정 프로세스의 CPU 과점유가 시스템 지연을 유발하는 과정

1. **실행 대기열 증가:** CPU를 사용하려는 작업이 많아지면 실행 대기열이 길어지고, 다른 프로세스가 CPU를 할당받기까지 기다리는 시간이 늘어난다.
2. **스케줄링 및 컨텍스트 스위칭 비용:** 실행할 작업을 전환하는 과정에서 레지스터와 실행 상태 등을 저장·복원하는 비용이 발생한다. 전환이 과도하면 실제 작업에 사용할 수 있는 시간이 줄어들 수 있다.
3. **캐시 효율 저하 가능성:** 작업 전환과 메모리 접근 패턴에 따라 CPU 캐시의 효율이 떨어지고 캐시 미스가 증가할 수 있다. 다만 캐시 미스가 항상 컨텍스트 스위칭 때문에 발생하는 것은 아니다.
4. **시스템 작업 지연:** 네트워크 처리, 로그 기록, 헬스 체크, SSH 접속 등을 담당하는 작업도 CPU를 기다릴 수 있어 서비스 전체의 응답성이 나빠질 수 있다.

## 5. 교착상태(Deadlock)와 프로세스 정체 진단

### 교착상태의 개념과 4가지 조건

Deadlock은 둘 이상의 프로세스나 스레드가 서로가 점유한 자원을 기다리면서, 관련 작업이 더 이상 진행되지 못하는 상태다.

교착상태가 성립하려면 일반적으로 다음 네 가지 조건이 동시에 충족되어야 한다.

1. **상호 배제(Mutual Exclusion):** 자원을 한 번에 하나의 프로세스 또는 스레드만 사용할 수 있다.
2. **점유와 대기(Hold and Wait):** 자원을 점유한 상태에서 다른 자원을 추가로 기다린다.
3. **비선점(No Preemption):** 점유 중인 자원을 외부에서 강제로 빼앗을 수 없다.
4. **순환 대기(Circular Wait):** 각 작업이 다음 작업이 점유한 자원을 기다리는 순환 구조가 형성된다.

### Deadlock과 일반적인 Hang의 차이

프로세스가 응답하지 않는다고 해서 모두 Deadlock인 것은 아니다.

| 구분 | 특징 |
|---|---|
| Deadlock | 서로 자원을 기다리는 순환 대기로 작업이 진행되지 않는다 |
| Infinite Loop | 종료 조건이 없는 반복 등으로 CPU를 계속 사용할 수 있다 |
| Blocking I/O | 파일, 디스크, 네트워크 등의 입출력 완료를 기다린다 |
| Starvation | 특정 작업이 자원을 계속 할당받지 못한다 |
| Livelock | 상태 변화나 재시도는 계속되지만 실질적인 작업 진전이 없다 |

Deadlock은 CPU 사용률이 낮은 상태로 나타날 수 있지만, 낮은 CPU 사용률만으로 Deadlock을 확정할 수는 없다. 스레드의 대기 상태, 락 소유 관계, 스택 트레이스 등 추가 증거가 필요하다.

### 시스템 도구를 활용한 진단

| 진단 항목 | 도구 | 확인할 내용 |
|---|---|---|
| 프로세스 상태 | `ps`, `top` | PID가 유지되는지, 프로세스 상태와 CPU 사용량이 어떤지 확인 |
| 스레드 상태 | `top -H`, `ps -L` | 스레드별 CPU 사용량과 상태 확인 |
| 대기 위치 | `/proc/PID/wchan`, `/proc/PID/task/TID/wchan` | 커널에서 어떤 대기 지점에 있는지 참고 |
| 시스템 콜 | `strace -p PID` | 어떤 시스템 콜에서 대기하거나 반복되는지 확인 |
| 파일·소켓 | `lsof -p PID` | 프로세스가 열어 둔 파일과 소켓 확인 |
| 스레드 스택·락 | `jstack`, `pstack`, `gdb` | 스레드 호출 스택과 락 대기 관계 분석 |

`futex(..., FUTEX_WAIT)`는 스레드가 동기화 객체를 기다리는 상황에서 나타날 수 있지만, 정상적인 락 대기에서도 발생한다. 따라서 이 시스템 콜 하나만으로 Deadlock이라고 판단하면 안 된다. 또한 `S`는 interruptible sleep, `D`는 uninterruptible sleep을 뜻하며, `D` 상태는 I/O 대기 등에서도 나타날 수 있다.

### 식사하는 철학자 문제

원탁에 앉은 다섯 명의 철학자가 식사하려면 양쪽 포크 두 개를 모두 사용해야 한다고 가정한다. 모두가 동시에 한쪽 포크를 집고 반대쪽 포크를 기다리면, 누구도 다음 단계로 진행하지 못하는 교착상태가 발생할 수 있다.

### Deadlock 대응 전략

| 전략 | 핵심 아이디어 | 대표 기법 / 예시 | 특징 |
|---|---|---|---|
| 예방(Prevention) | 네 가지 발생 조건 중 하나가 성립하지 않도록 설계 | 자원 획득 순서 통일, 점유 중 추가 자원 요청 제한 | 원천 차단에 유리하지만 설계 제약이 생길 수 있음 |
| 회피(Avoidance) | 자원 할당 후에도 안전 상태가 유지되는 경우에만 할당 | 은행원 알고리즘(Banker's Algorithm) | 자원 요구량을 사전에 알아야 하는 등 적용 조건이 까다로움 |
| 탐지 및 복구 | 교착상태를 탐지한 뒤 작업 중단 등으로 해소 | 대기 그래프 검사, 프로세스 또는 트랜잭션 중단 | 자원 활용은 유연하지만 복구 과정에서 작업 손실이 발생할 수 있음 |
| 무시(Ignorance) | 발생 가능성과 탐지 비용을 고려해 별도 대응을 두지 않음 | 타조 알고리즘(Ostrich Algorithm) | 구현 오버헤드는 낮지만 실제 발생 시 별도 대응이 필요함 |

## 6. 데이터 기반 장애 분석과 GitHub Issue 커뮤니케이션

장애 대응에서는 추측과 확인된 사실을 구분하고, 관측 가능한 증거를 바탕으로 원인을 좁혀야 한다.

### 증거 기반 분석

- **메트릭(Metrics):** 시간에 따른 수치 변화를 보여준다. 예를 들어 CPU 사용률, RSS, Load Average, 메모리 가용량, HTTP 5xx 비율 등이 있다.
- **로그(Logs):** 특정 시점에 애플리케이션이나 시스템에서 발생한 이벤트를 기록한다. 예를 들어 MemoryGuard 경고, Watchdog 종료 메시지, 오류 스택 트레이스 등이 있다.
- **트레이스(Traces):** 하나의 요청이 여러 서비스나 컴포넌트를 거치는 경로와 각 단계의 소요 시간을 추적한다. 분산 시스템에서 지연이 발생한 구간을 찾는 데 유용하다.

메트릭은 장애의 추세와 범위를 파악하는 데, 로그는 특정 이벤트의 맥락을 파악하는 데, 트레이스는 요청 처리 경로를 좁히는 데 도움이 된다.

### 육하원칙(5W1H) 기반 장애 기록

- **언제(When):** 장애 시작, 인지, 조치 시작, 복구 완료 시각
- **어디서(Where):** 환경, 서버 인스턴스, 컨테이너·Pod, API 엔드포인트
- **누가/무엇을(Who & What):** 영향을 받은 서비스 기능과 사용자·시스템 범위
- **어떻게(How):** 관측된 현상과 장애가 진행된 과정
- **왜(Why):** 로그와 메트릭으로 확인한 원인. 확인된 사실과 아직 검증되지 않은 가설을 구분

### GitHub Issue 작성 원칙

- **명확한 제목:** `[Incident] [대상 서비스] 핵심 현상 요약`처럼 대상과 현상을 드러낸다.
- **요약과 영향도:** 장애 현상, 영향 범위, 현재 상태를 상단에 배치한다.
- **증거 첨부:** 타임라인, 메트릭 그래프, 핵심 로그, 명령어 출력 등을 첨부한다.
- **원인과 가설 구분:** 확인된 사실, 원인으로 판단한 근거, 추가 확인이 필요한 가설을 구분한다.
- **조치와 후속 작업:** 임시 조치와 근본 해결책을 나누고 담당자, 라벨, 관련 PR을 연결한다. 해결 PR에는 필요에 따라 `Fixes #이슈번호`를 사용한다.

---

## 부록. 핵심 리눅스 진단 명령어

```bash
# 프로세스 상태와 메모리·CPU 사용량
ps -p PID -o pid,ppid,stat,%cpu,%mem,rss,vsz,etime

# 스레드별 CPU 사용량
top -H -p PID

# 시스템 메모리와 가용 메모리
free -h

# 시스템 Load Average
uptime

# 프로세스 메모리 상세 정보
cat /proc/PID/status

# 프로세스 메모리 매핑 요약
cat /proc/PID/smaps_rollup

# 커널 OOM 관련 로그 (권한 및 배포판 설정에 따라 접근 제한 가능)
dmesg -T | grep -Ei 'oom|killed process'

# 프로세스 시스템 콜 추적
strace -p PID

# 프로세스가 열어 둔 파일과 소켓
lsof -p PID
```

명령어 출력은 특정 시점의 스냅샷이다. 장애 원인을 분석할 때는 한 번의 출력만으로 결론 내리지 말고, 시간 간격을 두고 반복 수집한 결과와 애플리케이션 로그를 함께 비교한다.

---

## 학습 시 기억할 점

1. **메모리:** RSS·VSZ·PSS의 차이를 이해하고, 애플리케이션 자체 보호 정책과 커널 OOM Killer를 구분한다.
2. **CPU:** CPU 사용률, 스케줄링 대기, Load Average가 서로 다른 지표임을 이해한다.
3. **동시성:** Deadlock과 일반적인 프로세스 정체를 구분하고, 교착상태의 네 가지 조건을 설명할 수 있어야 한다.
4. **장애 분석:** 관측된 현상과 원인 가설을 구분하고, 여러 증거를 연결해 결론을 검증한다.
